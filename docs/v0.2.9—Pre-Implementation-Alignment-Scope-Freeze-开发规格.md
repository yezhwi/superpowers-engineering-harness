# Superpowers Engineering Harness v0.2.9 开发规格

> 版本：v0.2.9  
> 核心能力：Pre-Implementation Alignment & Scope Freeze  
> 状态：Implementation Specification  
> 面向：AI Coding Agent / 小模型实现者  
> 范围：Engineering Harness 控制面  
> 核心原则：**先对齐，再编码；先闭环，再 Implementation。**

---

# 1. 背景

当前 Engineering Harness 已经重点解决：

- Specification
- Implementation
- Verification
- Review
- Gate
- Evidence
- Context Recovery
- Task Complexity
- 长任务执行漂移
- Done 必须由 Evidence 定义

但仍存在一个上游问题：

**如果进入 Implementation 时，需求本身尚未完全闭环，那么后续再严格的 Verification / Review / Evidence，也只能证明“代码正确实现了某个方案”，无法证明“实现的是用户真正确认过的方案”。**

典型表现：

1. 开发过程中才发现 Scope 没定义。
2. 实现一半才询问用户关键决策。
3. Acceptance Criteria 在编码过程中不断变化。
4. Agent 自己补全用户没有确认的产品决策。
5. 实现过程中静默扩大 Scope。
6. 新会话或 Context Compression 后遗失之前确认的决策。
7. Requirement 有实现，但没有 Verification。
8. Verification 有测试，但无法对应 Acceptance Criteria。
9. Agent 一边设计、一边实现、一边修改需求。

因此 v0.2.9 在 Implementation 前增加正式的：

**Pre-Implementation Alignment & Scope Freeze**

其目标不是增加更多文档，而是建立一个正式的：

**Implementation Contract**

---

# 2. 设计来源

本能力蒸馏自 `grill-with-docs / grilling` 的核心思想，但不得直接复制其实现。

需要吸收：

1. 开发前解决设计决策。
2. 沿 Decision Tree 按依赖顺序解决问题。
3. 一次只处理一个真正需要用户回答的问题。
4. Codebase 可以回答的问题由 Agent 自行调查。
5. 用户决策必须提供 Options。
6. Agent 应提供 Recommendation + Reason。
7. 重要决策形成持久化记录。
8. Shared Understanding 达成后才能进入 Implementation。

Engineering Harness 在此基础上进一步增加：

- Scope Freeze
- Boundary Freeze
- Acceptance Criteria Closure
- Verification Closure
- Open Loop Detection
- Alignment Gate
- Scope Drift Detection
- Scope Change Protocol
- Context Recovery
- Q-Level 自适应
- Evidence Closure

因此本版本不是新增一个 `grill-with-docs` Skill。

而是：

> **将“开发前对齐”提升为 Harness 生命周期中的正式工程 Gate。**

---

# 3. v0.2.9 核心目标

必须实现以下目标。

## G1. Implementation 前完成需求对齐

进入 IMPLEMENTING 前必须明确：

- Goal
- Scope
- Non-goals
- Boundaries
- Constraints
- Assumptions
- Decisions
- Acceptance Criteria
- Verification Strategy

---

## G2. Facts 与 Decisions 分离

必须区分：

### Fact

可以通过以下方式确定：

- 读取代码
- 读取配置
- 读取 Harness Context
- 读取文档
- 运行安全的查询/检查

Fact 不应询问用户。

### Decision

存在多个合理方案，并且不同选择会改变：

- 用户行为
- Scope
- API Contract
- Data Contract
- Persistence
- Permission
- Architecture Boundary
- Acceptance Criteria
- Deployment / Compatibility

只有 Decision 才进入用户确认流程。

---

## G3. 建立 Alignment Gate

没有完成 Alignment 的任务不得进入 IMPLEMENTING。

最低要求：

```text
open_questions == 0
open_decisions == 0
open_loops == 0
```

并且所有必要字段完整。

---

## G4. 防止 Silent Scope Change

Implementation 开始后，Agent 不得静默修改已经冻结的：

- Scope
- Boundary
- User-visible behavior
- Contract
- Acceptance Criteria
- Critical Decision

如果必须修改：

```text
detect scope drift
        ↓
stop affected implementation
        ↓
record finding
        ↓
return ALIGNING
        ↓
user decision
        ↓
update contract
        ↓
Alignment Gate
        ↓
resume implementation
```

---

## G5. 建立开发前闭环

每个 Requirement 必须形成：

```text
Requirement
    ↓
Acceptance Criteria
    ↓
Implementation Surface / Seam
    ↓
Verification
    ↓
Expected Evidence
```

不能形成完整链路的 Requirement 属于 Open Loop。

---

# 4. 非目标

v0.2.9 不要求：

- 完整复制 Matt Pocock skills。
- 引入 `CONTEXT.md` 作为 Harness 核心文件。
- 所有 Decision 都生成 ADR。
- 所有开发任务都进行长时间访谈。
- 所有实现细节都需要用户确认。
- Implementation 后完全禁止修改计划。
- 自动决定产品需求。
- 自动扩大任务 Scope。
- 用 LLM 自我声明代替结构化 Gate。

尤其禁止把本功能实现成：

> “编码之前问用户很多问题。”

本版本真正目标是：

> **以最低必要交互成本建立可验证的 Implementation Contract。**

---

# 5. 生命周期

建议状态模型增加：

```text
INITIALIZED
     ↓
DISCOVERING
     ↓
ALIGNING
     ↓
SPECIFYING
     ↓
IMPLEMENTING
     ↓
VERIFYING
     ↓
REVIEWING
     ↓
GATING
     ↓
DONE
```

其中：

## DISCOVERING

Agent 调查 Facts。

例如：

- Repository structure
- Existing API
- Existing interfaces
- Current tests
- Existing conventions
- Relevant invariants
- Existing decisions

原则：

**能调查，不询问。**

---

## ALIGNING

只解决真正需要 Decision 的问题。

完成：

- Scope
- Boundary
- Non-goals
- Constraints
- Decisions
- Acceptance Criteria
- Verification strategy

---

## SPECIFYING

将已经确认的 Alignment Contract 转化成执行规格。

原则：

> SPECIFYING 不是重新做需求决策的阶段。

如果 Specification 阶段发现新的 Product / Scope Decision：

```text
SPECIFYING → ALIGNING
```

# 7. alignment.yaml

建议 Schema：

```yaml
version: 1

task_id: TASK-001

status:
  alignment: ready

goal:
  summary: ""

scope:
  in: []
  out: []

boundaries: []

constraints: []

assumptions: []

acceptance_criteria:
  - id: AC-001
    description: ""
    requirement_ids:
      - REQ-001

verification:
  - id: VER-001
    acceptance_criteria:
      - AC-001
    method: test
    command: ""
    expected_evidence: ""

implementation_surfaces:
  - id: SURFACE-001
    acceptance_criteria:
      - AC-001
    paths: []
    seam: ""

open_questions: []

open_decisions: []

open_loops: []

freeze:
  frozen: true
  frozen_at: ""
  contract_hash: ""
```

实际 Schema 应遵循当前项目已有 YAML / schema / serialization conventions。

不得为了本功能平行创建第二套配置体系。

# 8. decisions.yaml

用于持久化真正需要用户参与的 Decision。

示例：

```yaml
version: 1

decisions:

  - id: DEC-001

    status: accepted

    question:
      是否修改现有 API？

    context:
      当前 API 已存在外部调用方。

    options:

      - id: modify-existing
        description: 修改现有 API

      - id: add-new
        description: 新增 API

    recommendation:
      option: add-new
      reason: >
        可以避免破坏已有调用方，并降低兼容性风险。

    selected:
      option: add-new

    decided_by:
      user

    affects:
      - scope
      - api-contract

    reversible: false
```

---

# 9. Decision Interaction Protocol

当需要用户 Decision 时，Agent 必须输出：

```text
Decision
Context
Options
Recommendation
Reason
Impact
```

例如：

```text
需要确认一个接口设计决策。

A. 修改现有 DELETE API
B. 新增 archive API

推荐：B

原因：
当前 DELETE 已有调用方，新建 archive API 可以保持现有
contract 不变，同时满足新的归档语义。

影响：
API Contract / Compatibility / Tests
```

等待用户确认。

不得：

- 隐藏 Recommendation。
- 只问“你想怎么做？”
- 给大量没有实际意义的 Options。
- 替用户自动确认高影响 Decision。

---

# 10. Decision Tree

Decision 必须按依赖关系处理。

例如：

```text
是否支持 soft delete？
        ↓
YES
        ↓
是否允许恢复？
        ↓
YES
        ↓
恢复权限是什么？
```

不能一开始同时询问：

```text
Q1 soft delete?
Q2 restore?
Q3 restore permission?
Q4 retention?
Q5 API?
```

因为上游 Decision 可能消灭整个下游分支。

因此：

**一次只处理当前 Decision Frontier 上最重要的问题。**

# 11. Alignment Completeness

必须实现 Alignment Completeness Check。

逻辑概念：

```text
Goal                  ✓
Scope                 ✓
Non-goals             ✓
Boundaries            ✓
Constraints           ✓
Decisions             ✓
Acceptance Criteria   ✓
Verification          ✓
Open Questions        0
Open Decisions        0
Open Loops            0
```

不能简单依赖：

```text
agent says "requirements are clear"
```

必须通过结构化数据计算。

---

# 12. Alignment Gate

增加：

```text
ALIGNMENT_GATE
```

最低 Gate 条件：

```text
goal exists

scope defined

non-goals defined

required boundaries defined

acceptance criteria exists

open_questions == 0

open_decisions == 0

open_loops == 0

all requirements mapped

all AC mapped

verification strategy exists
```

Gate PASS：

```text
ALIGNMENT_READY
```

Gate FAIL：

```text
ALIGNMENT_BLOCKED
```

并必须返回：

```text
blocking reasons
missing fields
open decisions
open loops
recommended next action
```

# 13. Closure Graph

本版本最重要的数据关系之一：

```text
REQ
 ↓
AC
 ↓
SURFACE
 ↓
VERIFICATION
 ↓
EXPECTED EVIDENCE
```

例如：

```text
REQ-001
   ↓
AC-001
   ↓
SURFACE-001
   ↓
VER-001
   ↓
EVIDENCE-001
```

```text
EXPECTED EVIDENCE
```

Evidence 在 Implementation / Verification 后产生。

# 14. Open Loop Detection

以下均属于 Open Loop：

```text
REQ → no AC

AC → no REQ

AC → no Verification

Verification → no expected evidence

Critical Requirement → no implementation surface/seam
```

例如：

```text
REQ-003
 ↓
AC-005
 ↓
???
```

必须生成：

```text
OPEN_LOOP
```

并阻止 Alignment Gate。

---

# 15. Scope Freeze

Alignment Gate PASS 后：

```yaml
freeze:
  frozen: true
  frozen_at: "..."
  contract_hash: "..."
```

冻结对象至少包括：

```text
Goal
Scope
Non-goals
Boundaries
Critical Decisions
Acceptance Criteria
```

Verification implementation details 可以在允许范围内变化。

---

# 16. Implementation Freedom Boundary

Scope Freeze 不能导致 Agent 每个技术细节都询问用户。

以下默认属于 Implementation Freedom：

- private helper
- variable naming
- internal refactor
- fixture organization
- local algorithm choice
- private method decomposition
- equivalent implementation technique

前提：

```text
does not change frozen contract
```

---

# 17. Scope Drift

以下变化默认视为 Scope Drift：

- 新增用户可见行为
- 删除已确认行为
- 修改 API Contract
- 修改 Data Contract
- 修改 Permission Model
- 修改 Persistence Model
- 修改 Acceptance Criteria
- 扩大 Scope
- 删除 Scope
- 修改关键 Boundary
- 推翻用户确认的 Decision

---

# 18. Scope Change Protocol

检测到 Scope Drift 后禁止 Agent：

```text
直接修改 alignment.yaml
继续实现
最后才告诉用户
```

必须：

```text
IMPLEMENTING
      ↓
SCOPE_DRIFT detected
      ↓
create finding
      ↓
affected work blocked
      ↓
ALIGNING
      ↓
Decision Interaction
      ↓
update contract
      ↓
recalculate closure
      ↓
Alignment Gate
      ↓
freeze new contract
      ↓
IMPLEMENTING
```

建议 Finding：

```yaml
id: FND-SCOPE-001

type: SCOPE_DRIFT

severity: blocking

detected_during:
  IMPLEMENTING

current_contract:
  ...

proposed_change:
  ...

reason:
  ...

affected:
  - AC-003
  - API-CONTRACT

required_action:
  realign
```

## Q0


**Lightweight Alignment**


```text

```

不应强制用户进行 grilling。

## Q2

**Full Alignment**

```text

Non-goals

Constraints
Assumptions
Decisions
Acceptance Criteria
Implementation Surface
Verification
```

## Q3 / STRICT

**Full Alignment + Explicit Approval**

# 20. Auto Alignment

这是控制 Token 和用户交互成本的重要机制。

如果 Agent 能从以下信息完全确定：

```text
user request
+
repository
+
requirements
+
existing decisions
+
invariants
```

则允许自动生成 Alignment Contract。

例如简单 Bug Fix：

```text
按钮点击无响应
```

代码中已经可以确定：

```text
Goal
Scope
Expected behavior
Test
```

则：

```text
AUTO_ALIGNMENT
```

而不是强制询问用户：

> 请确认目标是什么？

---

# 21. Ask Only When Necessary

询问用户必须满足：

```text
cannot be resolved from facts
AND
multiple reasonable options exist
AND
choice affects frozen contract
```

否则：

```text
DO NOT ASK
```

这是本版本非常重要的 Token / UX Gate。

---

# 22. Context Recovery

Alignment Contract 必须成为 Context Recovery 的输入。

Context Compression / Session Restart 后优先恢复：

```text
current-task
requirements
invariants
alignment
decisions
gate
active findings
```

Agent 不应依赖：

```text
"我记得之前用户好像选择了..."
```

而应该读取：

```text
DEC-001.selected
```

恢复 Decision。

---

# 23. Contract Hash

Alignment Freeze 后建议生成：

```text
contract_hash
```

Hash 输入必须 canonicalize。

至少覆盖：

```text
scope
non-goals
boundaries
critical decisions
acceptance criteria
```

用途：

Implementation / Gate 阶段发现 Contract 被修改时：

```text
expected hash != current hash
```

触发：

```text
CONTRACT_CHANGED
```

注意：

Hash 不是 Scope Drift 的唯一检测机制。

语义变化检测仍需要结构化规则。

# 25. Gate 集成

现有 Gate 流程中增加前置约束：

```text
IMPLEMENTING transition
        ↓
Alignment Gate?
        ↓
PASS
        ↓
IMPLEMENTING
```

```text

```

则：

```text
transition rejected
```

# 26. 与 Test Plan Gate 的关系

Alignment Gate 不替代 Test Plan Gate。

两者关系：

```text
Requirement
    ↓
Alignment Gate
    ↓
Acceptance Criteria
    ↓
Verification Strategy
    ↓
Implementation
    ↓
Test Plan Gate
    ↓
Verification
    ↓
Evidence
```

Alignment Gate 回答：

> **我们到底准备实现什么，以及怎么证明它是对的？**

Test Plan Gate 回答：

> **具体测试计划是否足以验证这些 Acceptance Criteria？**

# 28. State Machine Requirements

实现模型必须检查现有 State Machine。

不得直接增加状态而破坏：

```text
BLOCKED recovery
VERIFYING
REVIEWING
GATING
```

至少测试：

```text
DISCOVERING → ALIGNING

ALIGNING → SPECIFYING

ALIGNING → IMPLEMENTING
```

如果项目允许 Q1 skip specification。

以及：

```text
SPECIFYING → ALIGNING
```

用于发现新 Decision。

以及：

```text
IMPLEMENTING → ALIGNING
```

仅允许：

```text
SCOPE_DRIFT
CONTRACT_CHANGE
NEW_REQUIRED_DECISION
```

等受控原因。

禁止把它变成任意回退通道。

# 30. Fail-Closed

以下情况必须 Fail Closed：

```text
alignment missing

alignment invalid

contract corrupted

critical decision unresolved

open loop exists

contract changed without re-alignment

required verification missing
```

不得：

```text
warning → continue implementation
```

---

# 31. Token Efficiency

本版本不能明显破坏 v0.2.8 的 Context / Execution Efficiency。

必须避免：

```text
每次状态转换重新读完整 repo

每次 alignment 重跑所有 discovery

重复询问已经确认的 decision

每次 context restore 重新 grilling

简单 Q1 强制 full alignment
```

应优先：

```text
persist facts

persist decisions

incremental validation

contract hash

targeted repository inspection

Q-level adaptive alignment
```

# 34. Acceptance Criteria

v0.2.9 完成必须满足：

## AC-01

Q2/Q3 任务在 Alignment 未完成时不能进入 Implementation。

## AC-02

## AC-07

## AC-11

Implementation Freedom 内部变化不会误报 Scope Drift。

## AC-12

Q1 不被强制进入 Full Alignment。

## AC-13

Alignment 不显著破坏 v0.2.8 Token Optimization。

## AC-14

Context Compression 后能够恢复 Alignment Contract。

现有 Gate / Evidence / Test Plan / Review 状态机测试不回归。

# 39. 核心设计原则

整个 v0.2.9 实现必须始终遵守以下原则。

## Principle 1

**先对齐，再编码。**

## Principle 2

**Facts belong to the Agent; Decisions belong to the User.**

## Principle 3

**能从代码和 Context 得到答案的问题，不询问用户。**

## Principle 4

**用户 Decision 必须提供 Recommendation + Reason。**

## Principle 5

**Implementation 前关闭所有关键 Open Loops。**

## Principle 6

**Implementation 可以自由实现，但不能突破冻结的 Contract。**

## Principle 7

**Scope Change 是合法事件，但 Silent Scope Change 不是。**

## Principle 8

**重新对齐必须通过正式状态迁移，而不是偷偷修改 Spec。**

## Principle 9

**Alignment 必须持久化，不能只存在于 Conversation Context。**

## Principle 10

**Alignment 的价值必须通过减少 Scope Drift 和 Rework 来证明，而不是通过增加流程来证明。**

# 40. v0.2.9 最终目标

v0.2.9 完成后，Engineering Harness 的工程闭环应从：

```text
Specification
      ↓
Implementation
      ↓
Verification
      ↓
Review
      ↓
Evidence
      ↓
Done
```

升级为：

```text
User Intent
      ↓
Discovery
      ↓
Alignment
      ↓
Scope Freeze
      ↓
Alignment Gate
      ↓
Specification
      ↓
Implementation
      ↓
Verification
      ↓
Review
      ↓
Evidence
      ↓
Completion Gate
      ↓
Done
```

形成两个正式闭环：

```text
┌────────────────────────────┐
│       INTENT CLOSURE       │
│                            │
│ Intent                     │
│   ↓                        │
│ Alignment                  │
│   ↓                        │
│ Scope / Decision / AC      │
│   ↓                        │
│ Verification Strategy      │
│   ↓                        │
│ ALIGNMENT GATE             │
└─────────────┬──────────────┘
              ↓
       IMPLEMENTATION
              ↓
┌────────────────────────────┐
│      EVIDENCE CLOSURE      │
│                            │
│ Verification               │
│   ↓                        │
│ Review                     │
│   ↓                        │
│ Evidence                   │
│   ↓                        │
│ COMPLETION GATE            │
└─────────────┬──────────────┘
              ↓
             DONE
```

最终目标不是让 AI Coding 增加一个需求访谈步骤。

而是：

> **让“开始编码”本身成为一个需要证据证明已经准备好的工程状态。**

即：

> **Before proving that we built it right, first prove that we agreed on what to build.**
