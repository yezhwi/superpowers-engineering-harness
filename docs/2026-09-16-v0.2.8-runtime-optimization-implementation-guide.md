# Engineering Harness v0.2.8 运行期优化实施指南

> 状态：Proposed
> 日期：2026-09-16
> 适用版本：v0.2.8
> 目标读者：执行 Harness 优化的小模型/编码 Agent
> 范围：Harness control-plane、CLI、evidence 与测试；不修改业务仓库产品代码。

## 1. 背景与目标

RClaw 实测显示 v0.2.8 的控制强度可用，但有若干运行期摩擦：compact context 载入无关历史对象、前端 Vitest evidence 不能稳定绑定、review scope 因顺序失败、已有实现的需求无法诚实进入 FAST 验证闭环。

本轮目标：

```text
降低无效 context、无效重跑和误导性 blocker；
不放宽 Gate、evidence freshness、finding closure 或 Q0 边界。
```

本文件是实施任务书。与现有 v0.2.8 契约冲突时，以 `Superpowers-Engineering-Harness-v0.2.8-Implementation-Contract.md` 为准；冲突项必须先更新契约，不得静默改实现。

## 2. 不变量

所有子项必须保持：

1. Q0 不读取 `.harness`、不创建或推进 task。
2. `.harness` authoritative state 不被 LLM 摘要替代。
3. 产品代码/测试变化仍必须使关联 build/test evidence stale。
4. control-plane 写入不得伪装成产品验证，也不得绕过 Gate。
5. 任何 test-plan binding 必须证明 runner 真正执行该 selector；不能只信任用户填入的路径。
6. path、contract ref、dependency ref 是不同类型；禁止混存后再按路径比较。
7. 未修改产品文件的“已有实现验证”不得要求伪造 RED 测试。

## 3. 优先级与交付拆分

按顺序实施。每项独立提交、独立回归，避免大型控制面重构。

| 顺序 | 编号 | 主题 | 价值 | 风险 |
|---|---|---|---|---|
| P0 | OPT-01 | Task-scoped compact context | 消除超长 context、timeout | 中 |
| P0 | OPT-02 | Vitest/npm evidence selector 解析 | 修复假性 coverage blocker | 中 |
| P0 | OPT-03 | Scope typed model 与无序比较 | 修复 review 假失败 | 低 |
| P1 | OPT-04 | Existing-implementation 验证路径 | 防止重复实现/伪造 RED | 中 |
| P1 | OPT-05 | classify 时提前风险 preflight | 提前暴露 Q1→Q2 升级 | 低 |
| P2 | OPT-06 | evidence/status 展示一致性 | 降低排障成本 | 低 |
| P2 | OPT-07 | 容器运行时 provenance | 提高证据可审计性 | 低 |

## 4. OPT-01：Task-scoped compact context

### 观察

新建 `TASK-1151` 后，`harness context --compact` 载入多个旧 task 的 `DEC-001..013`。这些 accepted decisions 不属于当前 task，却逐个触发 `DECISION_OUTSIDE_SCOPE` expansion；compact 命令首次运行超时，输出远超当前任务需要。

### 目标行为

- Layer 0 只内联当前 `task_id` 的 accepted decisions。
- 当前 task 显式 `supersedes`/`superseded_by`、contract ref、finding ref、impact ref 指向的跨 task 对象，可作为 Layer 2 reference 出现。
- 不因“仓库内存在旧 decision”自动扩大 context policy。
- `context --compact` 输出稳定：同一 authoritative state 多次运行，排序、omitted 与 expansion 原因一致。

### 建议修改点

优先检查：

- `src/harness/context.py`
- `src/harness/context_integrity.py`
- `src/harness/workspace.py`
- context 相关 schema/tests

实现：

1. 载入 decisions 后，先按 `decision.task_id == current_task.id` 过滤 Layer 0。
2. 建立 `referenced_decision_ids`，仅接纳当前 task 明确引用的跨 task decision。
3. 跨 task decision 只生成 `{id, ref, sha256, reason}`，不默认内联正文。
4. expansion 判断只遍历当前 Task Working Set 和显式引用对象。
5. `omitted` 记录过滤原因，例如 `different_task_not_referenced`。

### 验收测试

- 当前 task 有 1 个 decision、仓库有 100 个无关 historical decisions：compact Layer 0 仅含当前 decision。
- 无关历史 decision 不触发 context expansion。
- 显式引用跨 task decision 时，compact 有可解析 Layer 2 ref。
- 损坏的显式引用仍 fail-closed。
- compact 输出大小与运行时间受无关 decision 数量线性隔离；用 fixture 断言未读取/未序列化无关正文。

## 5. OPT-02：Vitest/npm evidence selector 解析

### 观察

以下命令真实通过，但 test-plan coverage 未被承认：

```sh
npm run test:unit -- --run src/__tests__/knowledgeBase-document-tree.spec.ts
```

临时改为 `npx vitest run ...` 才被 Harness selector parser 识别。这不应迫使项目改变标准测试入口。

### 目标行为

- Harness 可解析 `npm run <script> -- <vitest args>` 形式。
- 若 package script 最终执行 Vitest，canonical selector 必须按命令 cwd 解析到仓库 root-relative path。
- `covered_tests` 声明、命令 selector、test plan path 三者都必须匹配同一 canonical path。
- 无法静态解析 package script 时 fail-closed，报明确错误码；不得把任意 npm 命令当作测试。

### 建议修改点

优先检查：

- `src/harness/collect_evidence.py`
- package script 解析 helper
- `tests/` 中 evidence/test-plan 覆盖用例

实现：

1. 保留现有 `pytest`、`python -m pytest`、`npx vitest run` 解析。
2. 识别 `npm run NAME -- ...` 与 `npm run NAME -- --run ...`。
3. 从执行 cwd 的 `package.json` 读取 `scripts[NAME]`。
4. 仅在脚本 token 可确定包含 `vitest run` 或等价允许格式时提取 selector。
5. 对 shell wrapper 的 `sh -lc 'cd X && ...'` 先解出 cwd，再解析 package script。
6. 解析失败返回专用错误，例如 `TEST_RUNNER_UNRESOLVED`；错误需含 script 名和 package.json 相对路径，禁止回显无关环境变量。

### 验收测试

- `npm run test:unit -- --run src/a.spec.ts` 成功覆盖 `agents-frontend/src/a.spec.ts`。
- `npx vitest run src/a.spec.ts` 行为不回归。
- `npm run unrelated -- --run src/a.spec.ts` 不得声称覆盖测试。
- script 为非 Vitest 或 package.json 缺失时 fail-closed。
- 子项目 cwd 与仓库 root test-plan 路径等价。

## 6. OPT-03：Scope typed model 与无序比较

### 观察

diagnosability review 的 `review_scope.files` 与预期集合内容相同、顺序不同，仍报：

```text
DIAGNOSABILITY_SCOPE_MISMATCH
```

另有 `impact.contracts` 的文字契约标识进入 `review_scope.files`。它不是文件路径。

### 目标行为

- scope 比较按 canonical set，不按 YAML 输入顺序。
- `files` 只能存仓库内相对路径。
- contracts、dependencies、inspected paths 使用独立字段。
- CLI 错误输出 expected-only 与 actual-only 项，方便修复。

### 建议修改点

优先检查：

- `src/harness/workspace.py::project_task_scope`
- `src/harness/diagnosability.py`
- review schema 与测试

实现：

1. 引入明确 projection：`review_files`、`contract_refs`、`direct_dependencies`。
2. `review_files` 仅包含验证为仓库相对路径的项。
3. 比较时执行 path canonicalization、去重、排序，再比较集合。
4. schema 拒绝将 `DEC-*:` 文本放进 `review_scope.files`。
5. 兼容旧 artifact：读取时迁移/解释旧 contracts，不得静默把它们当路径。

### 验收测试

- 相同 files 的不同顺序通过。
- 重复 file path 规范化后通过或 schema 明确拒绝。
- contract label 在 files 中被拒绝，写入 `contract_refs` 后通过。
- 错误输出精确列出差异。

## 7. OPT-04：已有实现验证路径

### 观察

GitLab work item 1138 描述的 UI 功能已在 `origin/main`。若再创建 FAST task，正常行为没有 RED；强制 RED 会鼓励重复改动或伪造失败。

### 目标行为

支持“需求已实现”的可审计结论，不降低缺陷修复的 RED→GREEN 纪律。

建议新命令：

```sh
harness task verify-existing --reference origin/main --reason "work item already implemented"
```

此命令不是普通 implementation completion，也不是自动关闭 GitLab work item。

### 必填证据

1. 当前实现与 reference 的 target files diff 为空，或差异经用户明确接受。
2. 需求验收对应的 GREEN 测试/构建证据。
3. 引入实现的 commit/author/time，或无法追溯原因。
4. 结论类型：`already_satisfied`、`duplicate_request`、`requires_reproduction` 三选一。

### 状态规则

- 仅允许在 `CLASSIFIED` 或 `PLANNED` 使用。
- 不生成 fake finding，不要求 RED。
- 仅在写入完整 `existing_verification` 记录（reference、reason、`already_satisfied|duplicate_request` conclusion）时记录 `verification_mode: existing_implementation`；Gate 不能只信该字符串跳过 RED。
- Gate 仍检查 GREEN evidence、freshness、scope 与授权。
- 若 UI/API 行为与 work item 仍可复现不符，命令不写状态并保持 `CLASSIFIED`；创建或恢复 finding 后走正常 reproduce workflow。

### 验收测试

- 已实现目标文件与 reference 相同，GREEN evidence 完整：可产生 `already_satisfied` 结论。
- target diff 非空：需明确 reason/用户确认，否则阻断。
- 没有 GREEN evidence：阻断。
- 试图从该路径标记 GitLab issue closed：Harness 不执行 GitLab 写操作。

## 8. OPT-05：classify 时风险 preflight

### 观察

任务可先被分类为 Q1/FAST，随后 `context --compact` 才出现 `RISK_ESCALATION_REQUIRED`。用户已进入错误流程。

### 目标行为

`harness task classify --level Q1 ...` 在持久化前或原子持久化后立即执行 risk-boundary preflight。

- 若 FAST 合法：分类成功。
- 若需要 Q2：退出非 0，不持久化 Q1，返回升级原因和推荐命令。
- 若风险仅在后续 diff/impact 发现：保留既有 `harness task escalate` 路径。

### 验收测试

- 已知 Q2 boundary 的输入不能留下 Q1 task state。
- Q1 合法输入不回归。
- 后续新增 impact 风险仍能要求升级，不能被 preflight 绕过。

## 9. OPT-06：evidence/status 展示一致性

### 观察

`harness status` 可列出 FRESH build/unit evidence，但摘要字段仍显示 `Build unknown`、`Unit Tests unknown`。这会误导人工排障。

### 目标行为

摘要与 evidence 列表使用同一 resolver：同一时刻不得出现“FRESH 成功 build evidence”与“Build unknown”。

### 验收测试

- FRESH 成功 build/test evidence → 摘要为 passed/green。
- stale evidence → 摘要明确 stale，不显示 unknown。
- 多份 evidence → 输出选择依据（latest valid record path）。

## 10. OPT-07：容器运行时 provenance

### 观察

通过 `.devkind/kubectl exec ...` 运行测试时，evidence runtime 记录的是 Harness 宿主 Python，不是实际 frontend/app 容器。

### 目标行为

保留宿主 collector runtime，同时增加可选 execution provenance：

```yaml
execution_environment:
  transport: kubectl_exec
  namespace: coagents-dev
  workload: deploy/frontend
  container: frontend
  cwd: /workspaces/coagents_service/agents-frontend
```

解析不可靠时存 `transport: unknown`，不得猜测容器镜像、运行时版本或 kube context。

### 验收测试

- 标准 `kubectl -n NS exec deploy/NAME -- sh -lc 'cd PATH && CMD'` 采集 namespace/workload/cwd。
- 无 `-n`、多 container、非 kubectl 命令保持兼容。
- provenance 解析失败不改变 evidence 成功/失败语义。

## 11. 小模型执行协议

每个 OPT 必须按此顺序：

1. 读取现有 schema、CLI、实现和对应测试；先复用，不新建平行事实源。
2. 写/更新最小失败测试，证明本 OPT 的旧行为错误。
3. 仅修改本 OPT 所需模块；禁止顺手重构 controlplane。
4. 运行该 OPT 的定向测试，再运行受影响 Harness 测试集。
5. 检查旧 artifact 兼容性：已有 YAML/JSON 是否仍可读取；不能读取时必须提供明确 migration/error。
6. 验证 fail-closed：伪造路径、缺 package.json、坏 ref、旧 evidence 等反例必须被拒绝。
7. 更新本文件或对应版本契约、CHANGELOG、CLI help；未获授权不得 tag/release。

## 12. 最终验收矩阵

| 类别 | 必须证明 |
|---|---|
| 正确性 | 无关历史对象不污染当前 context；正确对象不被遗漏 |
| 安全性 | Q0、path boundary、schema 与 Gate 不放宽 |
| evidence | npm/Vitest、cwd、root-relative path 绑定正确且不可伪造 |
| 兼容性 | 旧 evidence/review artifact 有兼容读取或明确 fail-closed 迁移路径 |
| 可用性 | scope mismatch、runner unresolved、risk escalation 给出可执行错误信息 |
| 性能 | compact 不序列化无关 decision 正文；输出/耗时有 fixture 保护 |
| 回归 | `pytest`、现有 context/evidence/review/gate 测试全部通过 |

## 13. 非目标

- 不修改 RClaw 或任何业务项目代码。
- 不自动创建、关闭或回复 GitLab work item/MR。
- 不把 `covered_tests` 变成无命令证明的信任声明。
- 不因为已有实现路径而放宽正常 bugfix 的 RED→GREEN 纪律。
- 不将所有 `.harness` 内容从 integrity 检查排除。
- 不引入 LLM summary、embedding、vector DB 或全局搜索索引。
